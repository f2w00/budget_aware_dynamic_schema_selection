## 一、性能指标离线重算（B1/B3）

### 1. 吞吐聚合口径（问题 9）

论文主表采用 **mean-of-per-run**（每次运行先算吞吐再对 3 次取平均）；审稿人按 **pooled**（合并总成功数/总流水线时间）复算。两者对比率型指标天然不等，非算术错误。

| 方法 | 逐次吞吐 (rec/s) | mean-of-per-run | pooled | 主表值 |
|---|---|---|---|---|
| full | 9.0124 / 9.0265 / 9.1330 | **9.0573** | 9.0570 | 9.06 |
| budget-200 | 17.1328 / 17.7848 / 17.8983 | **17.6053** | 17.5988 | 17.61 |
| external-schemarag-k10 | 5.5139 / 4.5140 / 5.0705 | **5.0328** | 4.9991 | 5.03 |

逐次 pipeline_ms：full = 221917 / 221569 / 218986；budget-200 = 116735 / 112456 / 111742；schemaRAG = 362360 / 442619 / 394047。

**正文需明确**：`吞吐 = 每次运行 success / (pipeline_ms/1000)`，再对运行取平均；分母为**成功数**（非提交数）。

### 2. Token 口径拆分（问题 11）

- `full`、`budget-200` 无在线 embedding（embedding_ms=0），成本全为 LLM。
- `schemaRAG` 每条记录有在线 embedding（逐次累计约 249K / 304K / 222K ms）与 schema embedding（约 8.1K / 8.1K / 8.2K ms），但 **embedding 服务不返回 usage，日志无 embedding token 计数，token 数不可得**。

| 方法 | LLM-only total_tokens (mean) | 拆分 (in/out) | llm_ms_total (mean) | online_request_ms_total (mean) |
|---|---|---|---|---|
| full | 1,709,102 | 1,399,176 / 309,926 | 3,504,289 | 7,413,846 |
| budget-200 | 1,069,254 | 939,791 / 129,463 | 1,805,852 | 3,819,616 |
| external-schemarag-k10 | 1,230,411 | 1,019,842 / 210,569 | 6,314,844 | 13,367,333 |

> online_request_ms_total 含 queue_wait_ms（full≈3.69M、budget≈1.89M、schemaRAG≈6.11M）与 enqueue_blocked_ms，排队等待占主导。

**结论**：`Total tokens` 为 **LLM-only** 口径，已含重试累计；正文须声明 embedding token 不可得，不得把 LLM-only 误称全在线 Token。

### 3. 逐次运行值与不确定性（问题 12）

逐次吞吐与 pipeline_ms 见第 1 节。聚合块 `total_tokens` / `latency_p50` / `latency_p95` / `latency_p99` 均含 mean / sd / ci95（n=3，t=4.303）。示例（budget-200）：total_tokens mean=1,069,253.7，sd=6.1，CI95=[1,069,238.5, 1,069,268.8]。

### 4. P99 聚合方式（问题 13）

P99 = 每次运行内请求级 latency_ms（含失败/重试记录，取顶层累计值）分位数，再对 3 次取平均。

| 方法 | per-run latency P99 (ms) | P99 mean | P95 mean | P50 mean |
|---|---|---|---|---|
| full | 3612 / 3599 / 3592 | 3601 | 2438 | 1463 |
| budget-200 | 1445 / 1237 / 1240 | 1308 | 1161 | 893 |
| external-schemarag-k10 | 6418 / 32047 / 21191 | 19886 | 4572 | 2568 |

> schemaRAG P99 波动大（r2/r3 显著高于 r1），由长尾失败/重试驱动；P95 更稳定，建议正文同时报告 P95。

### 5. 失败、重试与绝对计数（问题 26 / 31）

3 次运行合计（N_total=6000/方法）：

| 方法 | N_total | N_success | N_error | 首次即成功 | 重试成功 | 最终失败 | retry_records | retry_count_total |
|---|---|---|---|---|---|---|---|---|
| full | 6000 | 6000 | 0 | 6000 | 0 | 0 | 0 | 0 |
| budget-200 | 6000 | 6000 | 0 | 6000 | 0 | 0 | 0 | 0 |
| external-schemarag-k10 | 6000 | 5994 | 6 | 5994 | 0 | 6 | 6 | 12 |

- 错误类型（schemaRAG，合并）：`ValueError: 返回了目标字段之外的键: ['artifact_id','年代','类型','详细描述']`，共 18 次 attempt（6 记录 × 3 attempts，重试也全部失败，**无一次重试成功**）。
- 重试附加成本（schemaRAG，逐次）：每次额外 input_tokens=1920、output_tokens=452、llm_ms≈8.8K / 11.4K / 11.3K。
- 主表需增加 `N_total`、`N_success`、失败数、重试数。

### 6. 口径声明（供正文/回复信引用）

1. **吞吐**：`success / (pipeline_ms/1000)`，逐次取平均；分母为成功数。
2. **Token**：LLM-only，来自 LLM API usage，已含重试累计；embedding token 不可得。
3. **P99**：每次运行内请求级分位数，再对运行取平均；含失败与重试记录。
4. **失败/重试**：顶层 token/时长字段为 attempts 累计和；首次失败、重试成功、最终失败按 attempts 状态判定。

### B5 一次性成本盈亏平衡点分析

**一次性成本**（B4）：训练 737.13ms + 加载 178.26ms ≈ **915.39ms**；离线训练（`llm_calls=False`）不消耗在线 API token，故一次性 **token 成本 = 0**。

**每记录在线成本**（来自 B1/B3 主实验 2000 条、3 次重复取均值）：

| 方法 | 时间 (ms/记录) | token/记录 | 吞吐 (rec/s) |

| budget-200 | 56.80 | 534.63 | 17.6053 |
| external-schemarag-k10 | 198.70 | 615.21 | 5.0328 |

**规模-总成本曲线**（一次性成本仅在 budget-200 计入）：

| 记录数 N | full 时间(s) | budget-200 时间(s) | schemaRAG 时间(s) | full token | budget-200 token | schemaRAG token |
|---|---|---|---|---|---|---|
| 50 | 5.52 | 3.76 | 9.93 | 42,728 | 26,731 | 30,760 |
| 100 | 11.04 | 6.60 | 19.87 | 85,455 | 53,463 | 61,521 |
| 500 | 55.20 | 29.32 | 99.35 | 427,276 | 267,313 | 307,603 |
| 1,000 | 110.41 | 57.72 | 198.70 | 854,551 | 534,627 | 615,206 |
| 2,000 | 220.82 | 114.52 | 397.39 | 1,709,102 | 1,069,254 | 1,230,411 |
| 10,000 | 1,104.08 | 568.93 | 1,986.97 | 8,545,512 | 5,346,268 | 6,152,055 |
| 100,000 | 11,040.81 | 5,681.02 | 19,869.72 | 85,455,117 | 53,462,683 | 61,520,550 |

**盈亏平衡点（break-even）**：

- **时间维度**：budget-200 相对 full 的 break-even 在 **N≈17 条**（`915ms / (110.41-56.80)ms`）。超过约 18 条记录后，budget-200 总墙钟时间严格更低；一次性成本随即摊销。
- **Token 维度**：budget-200 每记录省 319.9 token 且离线训练不消耗在线 token，故 **token 上对 full 严格占优（break-even N=0）**，无回收门槛。
- **SchemaRAG vs full（时间）**：SchemaRAG 每记录时间（198.7ms）高于 full（110.4ms），吞吐更低，**时间上从不优于 full**。

**质量权衡（B5 必须说明）**：成本占优不等于无条件胜出。在 476 对齐质量样本上，budget-200 的 `presence_f1`（0.7759）略高于 full（0.7623），但 `exact_value_recall`（0.6213 vs 0.6528）与 `gold_coverage`（0.8303 vs 1.0）低于 full；SchemaRAG k10 三项质量均低于 full（0.7069 / 0.4796 / 0.8078）。因此 budget-200 的盈亏平衡是**以少量字段精确召回/覆盖为代价**换取的，是否划算取决于应用对字段完整性的容忍度，正文须同时报告成本与质量，不作单一货币化取舍结论。

> **样本范围声明**：性能 2000 条（`stratified_raw_length`）与质量 476 条（`gold_main` 对齐子集）样本不同，token/条两批不一致；成本曲线用性能批次、质量用质量批次，不作跨批次严格显著性比较。

## 四、并发/队列解耦扫描（C3）

对应审稿问题 **15**。回应"当前仅有 c=1,q=1 与 c=32,q=32 两个联合端点，无法识别 Consumer、队列、背压和服务端排队的独立影响"。

### 设计：固定一个维度，扫另一个（budget-200，limit=500，temperature=0.0）

- **Set A（固定并发 c=16，扫队列 q∈{4,8,16,32,64}）**：隔离队列容量影响。
- **Set B（固定队列 q=16，扫并发 c∈{1,2,4,8,16,32}）**：隔离 Consumer 并发影响。
- 输出 `benchmarks/analysis/c3_scan/`：`c3_scan.json`、两张 CSV、两张图（`c3_fixed_c_scan_q`、`c3_fixed_q_scan_c`）。
- 生成脚本 `benchmarks/analyze_c3_scan.py`（离线读 raw+meta，不触发 LLM/embedding）。

> **数据说明**：Set A 的 q64 原始记录 `submitted=182` 被 shell 超时打断（不可用），采用干净重跑（`setA-q64-rerun`，`submitted=500`）。

### Set A：固定并发 c=16，扫队列 q

| q | 吞吐 (rec/s) | P50 (ms) | P95 (ms) | P99 (ms) | queue_wait P99 (ms) | producer_blocked (s) | 成功率 |
|---|---|---|---|---|---|---|---|
| 4 | 21.04 | 685 | 915 | 1156 | 578 | 20.7 | 500/500 |
| 8 | 21.31 | 683 | 904 | 1090 | 758 | 20.1 | 500/500 |
| 16 | 21.54 | 679 | 903 | 1078 | 997 | 19.5 | 500/500 |
| 32 | 20.20 | 765 | 1010 | 1181 | 1908 | 20.3 | 500/500 |
| 64 | 21.01 | 681 | 916 | 1166 | 3265 | 18.1 | 500/500 |

**观察**：c 固定时，吞吐在 q=4..64 间**基本持平（20.2–21.5 rec/s，±3%）**，队列容量不构成吞吐瓶颈；主要影响是**队尾延迟**——`queue_wait P99` 随 q 单调上升（578→3265ms），q 越大积压任务越多。`producer_blocked` 恒定约 18–21s，说明生产者因队列满被阻塞的时间与 q 无关（受并发消费速率约束）。

### Set B：固定队列 q=16，扫并发 c

| c | 吞吐 (rec/s) | P50 (ms) | P95 (ms) | P99 (ms) | queue_wait P99 (ms) | producer_blocked (s) | 成功率 |
|---|---|---|---|---|---|---|---|
| 1 | 1.67 | 564 | 756 | 790 | 11010 | 286.1 | 500/500 |
| 2 | 3.34 | 565 | 766 | 790 | 5512 | 141.5 | 500/500 |
| 4 | 6.52 | 568 | 777 | 800 | 2915 | 70.7 | 500/500 |
| 8 | 11.80 | 671 | 816 | 909 | 1783 | 37.8 | 500/500 |
| 16 | 21.54 | 679 | 903 | 1078 | 997 | 19.5 | 500/500 |
| 32 | 30.19 | 995 | 1321 | 1475 | 1188 | 13.0 | 500/500 |

**观察**：q 固定时，吞吐随并发**近似线性增长**（c=1→32：1.67→30.19 rec/s，约 ×18）；P50 在 c≤16 保持 ~565–680ms，到 c=32 升至 995ms、P99 升至 1475ms，**饱和点开始显现**。`producer_blocked` 随并发单调下降（286→13s），因为消费更快、队列更不易积满。全程 100% 成功率。

### 结论（可回填正文/回复信）

- **并发（Consumer 数）是吞吐的主导因素**：c 翻倍吞吐近似翻倍，q 变化几乎不影响吞吐。
- **队列容量主要影响队尾延迟（排队积压），不构成吞吐瓶颈**：q 从 4 增至 64，吞吐不变但 queue_wait P99 增 5.6 倍。
- 本实现为**单进程异步 Runner**，饱和出现在高并发端（c=32 尾延迟抬升）；当前收窄定位"单进程工程观察、非生产级扩展性"依然成立（见"当前可维持的结论边界"）。

### 5.1 适配代码与算法（external_schemarag_selector.py，git 已跟踪）

- 常量：`K=10`、`NAME_WEIGHT=0.5`、`DEFINITION_WEIGHT=0.5`、`QUERY_INSTRUCTION="给定一条文物原始记录，检索该记录中可能存在可靠信息的目标字段。"`。
- 流程（`select_fields`）：
  1. **字段（行）embedding**：对每个字段分别 embed `"字段名：{f}"` 与 `"字段定义：{def}"`，按 `NAME/DEFINITION_WEIGHT` 加权后 L2 归一化。字段向量绑定 `config_hash` 缓存，命中时 `schema_embedding_ms≈0`。

## 七、近重复检测与分组隔离可行性（C1）

> 回应审稿问题 19/20。脚本 `benchmarks/analyze_c1_near_duplicate.py`（纯离线，字符 3-gram Jaccard，倒排索引加速）。产出 `benchmarks/analysis/c1_near_duplicate/c1_near_duplicate.json`。

### 7.1 方法与数据

- 对 2000 条性能负载记录拼接「类型 + 文物名称 + 详细描述」做字符 3-gram Jaccard 相似度；用倒排索引仅比较共享 ≥1 个 n-gram 的候选对。
- 近重复阈值 Jaccard ≥ 0.6；对近重复对做并查集聚类。
- 用「类型 × 年代」组合作为机构/模板/批次元数据不可得（脱敏）时的批次代理聚类。

### 7.2 结果

| 指标 | 数值 |
|------|------|
| 记录总数 / 唯一 artifact_id | 2000 / 2000 |
| 近重复对（Jaccard ≥ 0.6） | 1101 |
| 近重复相似度范围 | 0.600 – 1.000（均值 0.687） |
| 近重复簇（size>1） | 111 |
| 最大簇大小 | 50（新石器时代细石器） |
| 类型×年代批次（组合数 / >1 条批次） | 239 / 132 |

### 7.3 近重复示例（最大两簇）

- **簇大小 50（玉石 / 新石器时代细石器）**：如 id 603「新石器时代细石器」，仅尺寸（长 2.9/3.0/1.9/2.1 厘米）不同的近相同模板描述。
- **簇大小 25（铜器 / 民国铜镜）**：如 id 4854/4836/4802/4863「民国铜镜/民国素铜镜/民国仿汉小铜镜」，同年代同类的模板化记录。

### 7.4 结论（可回填正文）

- 所有 artifact_id 唯一、无完全重复文本，但存在 **大量近重复模板簇**（111 簇，最大 50 条）——同一类型+年代+名称词干的模板化描述，仅尺寸等少量字段变化。
- 这证实了审稿人担忧的「模板/批次级泄漏」真实存在：简单的唯一 id 检查不能排除同藏品/模板/批次记录间的信息泄漏。
- **group-held-out 划分可行**：可按 132 个「类型×年代」批次或 111 个近重复簇做分组隔离；但真实来源/机构分组需原始元数据（当前脱敏数据仅能文本 + 类型×年代代理）。
- 建议正文明确：当前随机 ID 划分存在模板级近重复泄漏风险，性能/质量结论为「开发分布 + 模板近重复」下的观察，不宣称严格独立泛化。

## 八、训练规模与负载覆盖说明（A2 澄清）

> 审稿问题 4/21/27/34：主实验在线负载来自训练集与验证集，审稿人担心"未见负载"与"训练泄漏"。本节不加重跑，仅从训练口径上说明：M1 字段选择器用小规模训练、在更大分布上评估**机制收益**，其与 2000 条负载的部分覆盖符合预期。**纯文档澄清**，不依赖新增数据。

### 8.1 M1 训练规模的两个层次

本工作有两类字段选择器产物，需区分：

- **部署模型** `models/field_selector/`：`train/val/test = 5410 / 677 / 676`，seed 42，`trained_at=2026-08-30`。用于主实验在线运行的字段选择。
- **小样本模型** `models/training_size_ablation/100/seed_42/`（n100）：100 条训练，seed 42，`sampling=nested_multilabel_deficit_greedy`。用于训练规模敏感性 / 一次性成本计时（B4）与机制评估。

二者均为 `LogisticRegression(class_weight=balanced, solver=liblinear)` + TF-IDF `char ngram(2,5), min_df=2, max_features=100000, sublinear_tf`，同一特征与模型族。

### 8.2 负载与训练集覆盖实测

- 2000 条性能负载：`source_ids_files=[train_ids.json, validation_ids.json]`，exclude `test_ids.json`，seed 20260904。实测 `perf ∩ train = 1760`、`perf ∩ val = 240`、`perf ∩ test = 0`。
- 负载与 **n100 训练集**（100 条全来自 train）重叠 = **34 / 2000 = 1.7%**。
- 作为对照，负载与**部署模型 5410 训练集**重叠 = 88%。

### 8.3 为何 1.7% 覆盖符合预期

本工作评估的是**字段选择机制的收益**，而非字段选择器的独立泛化能力：

- M1 在数据集的一个子集（n100）上学习"选哪些字段更省 token / 更快"的选择策略，再在整个数据集分布上评估该机制带来的 token / 成本 / 吞吐 / 质量收益。
- 这是"机制收益评估"的标准口径：训练与评估样本**同分布**，且允许评估覆盖训练子集。负载对 n100 训练集 1.7% 的覆盖，反映的是"策略已在部分样本上见过该分布"这一**预期设计**，而非测试集泄漏。
- 若以 5410 全量训练的部署模型论，负载覆盖达 88% 才构成需警惕的开发分布偏差；这正是正文应区分"选择器训练规模"与"选择机制评估"两个层次的原因。

### 8.4 正文措辞建议

明确本工作定位为**字段选择机制的收益评估**（用训练子集学策略、全分布评估机制收益），并报告 n100 训练集与 2000 条负载的 1.7% 覆盖以量化该口径；不宣称选择器的严格独立泛化性能。
