# n=100 三方法配对流水线实验记录

## 1. 实验目的

在同一冻结负载、同一模型服务和同一并发配置下，直接比较以下三种记录级 Schema
策略的在线端到端表现：

```text
clean full
n=100 M1 + budget-200
SchemaRAG k=8
```

本实验用于替代此前不同时间段运行的 2,000 条流水线方法对照。此前的 clean-full
和 SchemaRAG 独立 cohort 保留为历史证据，但不与本实验合并统计。

## 3. 运行矩阵

共 6 个完整 block，每个 block 内三种方法连续串行运行，并共享同一冻结输入顺序。
每个 block 产生 3 个 run，每个 run 2,000 条，因此正式逻辑请求总量为：

```text
6 block × 3 method × 2,000 records = 36,000 requests
```

顺序平衡如下：

| Block | Seed | Repeat | 方法顺序 |
| ---: | ---: | ---: | --- |
| 1 | 42 | 1 | full -> budget-200 -> SchemaRAG k=8 |
| 2 | 43 | 1 | budget-200 -> SchemaRAG k=8 -> full |
| 3 | 44 | 1 | SchemaRAG k=8 -> full -> budget-200 |
| 4 | 44 | 2 | full -> SchemaRAG k=8 -> budget-200 |
| 5 | 43 | 2 | SchemaRAG k=8 -> budget-200 -> full |
| 6 | 42 | 2 | budget-200 -> full -> SchemaRAG k=8 |

每种方法在三个位置各出现两次。统计单位为 6 个完整 block；2,000 条记录不是
2,000 个独立统计重复。

## 4. 方法实现口径

### 4.1 clean full

- 不加载 M1；
- 不执行字段预测；
- 每条记录保留完整 18 字段；
- `prediction_ms=0`；
- `selector_model_dir=null`；
- `estimated_field_cost=null`。

### 4.2 n=100 M1 + budget-200

- 使用 `models/model_strategy_ablation/m1/seed_42`、`seed_43` 或 `seed_44`；
- 分类器和长度回归器均来自对应 n=100 训练模型；
- 记录级动态字段选择受 budget-200 约束；
- 选择结果通常为 6--9 个字段；
- 该方法包含 M1 字段预测和预算选择的本地 Producer 成本。

### 4.3 SchemaRAG k=8

- 使用字段名和字段定义的 Embedding 进行字段检索；
- 字段名/定义按 0.5/0.5 加权并 L2 归一化；
- raw record 与固定检索指令生成 query embedding；
- 与 18 个字段向量计算归一化点积并选择 Top-8；
- 不加载 M1，不执行字段预测；
- `prediction_ms=0`；
- `selector_model_dir=null`；
- `estimated_field_cost=null`；
- query embedding 计入在线流水线和记录级端到端时间；
- Schema 向量缓存/构建时间单独记录；
- 没有字段分段、示例检索或二阶段重排序；
- 当前实现是外部独立重实现，不是官方实现复现。

以下均为 6 个 block 的运行级均值；区间和标准差见统计 JSON。

| 方法 | Pipeline 时间 (s) | SD (s) | 吞吐 (records/s) | 总 Token | E2E P95 (ms) | E2E P99 (ms) | Embedding 时间 (s) |

相对于 clean full 的 6-block 配对差异：

| 方法 | Pipeline 时间变化 | Token 变化 | E2E P95 变化 | E2E P99 变化 |
| --- | ---: | ---: | ---: | ---: |
| budget-200 | 节省 147.556 s | 节省 684,031.8 | 节省 2,822.8 ms | 节省 3,281.1 ms |

## 8. 额外字段审计

允许额外字段的目的，是避免由于模型返回非目标字段而把整条记录判为失败；额外字段
仍然写入 `unexpected_fields`，并单独统计。

正式 12,000 条记录/方法的记录级额外字段情况：

| 方法 | 含额外字段记录数 | 记录级比例 | 额外字段出现次数 |
| --- | ---: | ---: | ---: |
| clean full | 1 | 0.0083% | 1 |
| budget-200 | 0 | 0% | 0 |
| SchemaRAG k=8 | 557 | 4.6417% | 1,099 |

SchemaRAG 额外字段出现次数：

```text
artifact_id: 557
年代: 518
类型: 12
详细描述: 12
```

这些字段未进入选定的 8 字段输出，但其出现已保留在原始 JSONL 中。由于三种方法
均无错误且成功率为 100%，允许额外字段策略没有改变成功/失败统计；它反映的是
SchemaRAG k=8 下模型输出约束的审计现象。

## 10. 结果边界

- 该实验支持当前冻结负载、当前模型服务和当前单进程流水线下的端到端描述性比较；
- 不能据此证明跨服务、跨硬件或跨数据集的普遍性能优势；
- 2,000 条负载来自 Train/Validation，适用于同域系统性能验证，不是未见泛化质量集；
- 本实验没有独立人工 Gold，不能用性能数据证明语义质量保持；
- SchemaRAG 是外部独立重实现，结果受当前 Embedding 服务、缓存和 query 构造影响；
- `record_end_to_end_ms` 是从 Producer 任务开始到结果写出的记录级计时，
  `latency_ms` 仍主要表示请求、解析和重试阶段，两者不能混称；
- 6 个 block 是运行级重复，不能把每条记录当作独立统计样本；
- API 货币价格、环境启动、容器启动、数据库冷缓存和完整银标生成成本未纳入；
- n=100 表示 M1 模型参数拟合使用 100 条训练记录，不代表整个开发流程只需 100 条
  标注，因为离线阈值校准使用独立 Validation 集。
