# 第二部分启动成本摊销与性能领先分析

## 1. 分析目的

本记录根据已经完成的在线流水线实验和本地初始化成本实验，估算将 M1 训练、模型加载等启动成本
纳入后，`budget-200` 相对于 `full` 的性能领先是否仍然成立，以及需要处理多少条记录才能覆盖
这些一次性成本。

本分析不发起新的 LLM 或 embedding 调用，所有数字来自以下已有产物：

- `doc/第二部分M1初始化成本实验记录.md`；
- `benchmarks/analysis/initialization/initialization_cost.json`；
- `benchmarks/analysis/performance/performance_statistics.json`；
- `benchmarks/runs/main-comparison-pro/summaries.json`。

## 2. 启动成本口径

本地实测结果如下：

| 成本 | 实测时间 | 性质 |
| --- | ---: | --- |
| 100 条 M1 模型训练 | 约 0.737 s | 离线一次性成本 |
| 已部署 M1 模型冷加载 | 约 0.178 s | 每个进程启动一次 |
| 训练后首次加载合计 | 约 0.915 s | 保守的完整初始化假设 |
| 100 条 `full` 本地规划 | 0.367 s | 在线 Producer 本地开销 |

训练和加载成本属于一次性成本。正常部署通常使用已经训练好的模型，因此实际新进程启动更接近
0.178 s；0.915 s 是假设每个比较周期都重新训练并加载模型的保守上界。

## 3. 主实验中加入启动成本

主实验固定为 2000 条记录、`c=16,q=16`。三次重复均值为：

| 方法 | 在线流水线时间 | 加入 0.915 s 后 | 有效吞吐 |
| --- | ---: | ---: | ---: |
| `full` | 220.82 s | 221.74 s | 9.06 records/s |
| `budget-200` | 113.64 s | 114.56 s | 17.61 records/s |

加入保守启动成本后，两者时间差约为 107.18 s，`budget-200` 仍保持明显领先。0.915 s 仅占
`budget-200` 主实验总时间约 0.8%，占 `full` 约 0.4%。

更重要的是，在当前实现中，`full` 和 `budget-200` 共用同一个 M1 模型。因此真实公平比较中，
训练和加载成本是共享成本，不能作为只针对 `budget-200` 的额外惩罚。将完整启动成本全部加到
`budget-200` 一侧，是更保守但不对称的敏感性分析。

## 4. 100 条记录的 break-even 分析

根据主实验有效吞吐换算：

| 方法 | 100 条在线时间 |
| --- | ---: |
| `full` | 约 11.04 s |
| `budget-200` | 约 5.68 s |

因此 100 条记录的在线时间差约为：

```text
11.04 - 5.68 = 5.36 s
```

如果采用最保守的不对称假设，即仅让 `budget-200` 额外承担完整的 0.915 s 初始化成本，则：

```text
每条节省时间 = 5.36 / 100 = 0.0536 s
break-even 条数 = 0.915 / 0.0536 = 17.1
```

所以处理约 **18 条记录**后，`budget-200` 即可覆盖一次完整的 M1 训练加加载成本。

若模型已经训练完成，只计算 0.178 s 冷加载成本：

```text
0.178 / 0.0536 = 3.3
```

约 **4 条记录**即可覆盖模型加载成本。

这两个 break-even 数字是保守敏感性分析。公平比较中两种方法共享同一模型时，启动成本对方法间
时间差基本没有影响，严格来说不存在需要由 `budget-200` 单独回收的启动成本。

## 5. 与本地规划成本的关系

100 条 `full` 本地规划总计 0.367 s，其中 M1 字段预测约 3.04 ms/条，Prompt 构造约 0.05 ms/条。
这部分已经包含在 Runner 的 Producer 规划阶段中，不能在既有 `full` 在线流水线时间上再次累加。

主实验配置下，100 条 `full` 在线端到端时间约 11.04 s，本地规划约占 3.3%。训练与加载则应按
部署周期或处理规模摊销：

```text
单条摊销成本 = 训练时间 / 累计服务记录数
             + 加载时间 / 单进程处理记录数
```

## 6. 结论边界

- 现有实验足以支持 `budget-200` 在纳入启动成本后仍领先的结论；
- 主实验中 `budget-200` 相对 `full` 的流水线时间降低约 48.54%，有效吞吐提高约 94.38%；
- 启动成本不应重复计入每条记录，也不应与在线 Token 成本混合；
- 18 条和 4 条是基于当前主实验吞吐的估算，不代表其他模型、硬件、服务端状态或并发配置；
- 该分析未测量环境安装、容器启动、数据库冷缓存和多进程并行加载。
