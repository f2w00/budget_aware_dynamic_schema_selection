# 第二部分：动态 Schema 流水线实验记录

## 1. 研究目标与系统边界

本部分评估动态 Schema 驱动预处理流水线的端到端系统性能，不重复第一部分字段级质量评价。
方法配置在性能实验前冻结；质量结果仅作为进入本部分比较的前提。

核心问题是：在相同输入、模型、并发与队列资源预算下，`budget-200` 相对于完整 Schema
基线 `full` 和外部 SchemaRAG 是否具有更低 Token 消耗、更短端到端时间和更高有效吞吐。

当前系统的准确称谓为**单进程异步有界 Producer-Consumer 流水线**，不宣称为完整分布式系统：

- Producer 按冻结 ID 输入顺序流式读取数据库记录并增量构造任务；
- 有界 `asyncio.Queue` 提供背压；
- Consumer 并发调用 OpenAI-compatible API，负责超时、解析、字段校验与有限重试；
- Writer 以 JSONL 追加结果，支持按配置哈希断点续跑；
- 尚未实现多进程/多节点分片、协调、合并或分布式恢复语义。

## 2. 实现与遥测

相关实现：

- `llm_runner.py`：流式任务生产、异步队列消费、重试、结果写入与任务级遥测；
- `external_schemarag_selector.py`：区分在线 query embedding 与 Schema 向量缓存开销；
- `benchmarks/benchmark_pipeline.py`：按方法、并发、队列和重复次数编排，保存原始结果、日志、
  元数据、完整性校验与汇总；
- `benchmarks/create_performance_workload.py`：构建并冻结独立性能工作负载。

任务级指标：

- 规划：`prediction_ms`、`selection_ms`、`prompt_build_ms`、`planning_ms`；
- 在线检索：`embedding_ms`、`schema_embedding_ms`；
- 请求：`llm_ms`、`parse_validate_ms`、`retry_backoff_ms`、`latency_ms`；
- 队列：`queue_wait_ms`、`enqueue_blocked_ms`；
- 结果：Token、成本、重试次数、状态、P50/P95/P99、CV、tail ratio。

运行级指标：`queue_peak`、`queue_average`、`producer_blocked_ms`、`consumer_idle_ms`、
`rss_peak_bytes`、`rss_average_bytes` 和 `rss_samples`。

`selection_ms` 包含 SchemaRAG 的 `embedding_ms`，报告时不得将二者相加。在线 query embedding
计入端到端性能；Schema 字段向量缓存读取或构建时间以 `schema_embedding_ms` 单列，不重复计入
每条在线检索成本。

### 2.1 在线流水线的计时边界

本部分报告的 `pipeline_ms` 和 makespan 只覆盖在线推理流水线：从性能工作负载开始被
读取、任务被规划并进入队列，到 LLM 请求、重试、结果解析校验和 JSONL 写入完成。模型
加载、Prompt/Schema 配置读取以及运行前的静态准备不计入该时间。

以下一次性启动成本也不计入本文的在线性能结果：

- 100 条 FullSchema 启动样本的生成时间（若该样本需要在线生成）；
- 训练数据构造和银标标签生成时间；
- M1 字段选择器的离线训练时间；
- 训练模型和相关向量器的加载时间。

因此，本部分的 Token、makespan 和有效吞吐均应称为**在线推理阶段指标**，不应写成
包含训练阶段的全生命周期成本。当前 M1 训练使用预先存在的 `training_dataset.jsonl`，
训练过程本身没有调用 LLM；第一部分已经验证的是小样本启动方案的离线训练和在线抽取
表现，二者不应在本部分的 `pipeline_ms` 中重复计入。

如果后续需要报告全生命周期成本，应单独定义启动成本并按性能负载记录数摊销：

```text
amortized_lifecycle_cost
    = one_time_startup_cost / workload_record_count
      + online_inference_cost_per_record
```

该公式目前只作为成本口径说明，不改变已经完成的性能统计，也不要求重新运行本部分
核心实验。

## 4. 前期验证与预扫描

### 4.1 10 条小规模基准

早期在 `data/splits/test_ids.json` 前 10 条上执行了 `full` 与 `budget-200` 的 72 次小矩阵：
并发 `1/2/4/8`，队列容量为 `concurrency x {1, 2, 4}`，每种配置重复 3 次。

- 72 个运行全部通过完整性验证，共 720 条均成功，无错误或重试；
- 10 条负载中，`full` 总 Token 约 8571，`budget-200` 约 5845，减少约 31.8%；
- 同配置下，`budget-200` 的流水线时间减少 43.0%--66.6%，有效吞吐提高 75.7%--187.7%；
- 队列容量不存在单调收益，不能据此预设更大队列更优；
- 高并发 `full` 存在明显服务端延迟波动，因此该矩阵仅用于验证框架与探索，不作为正式主结论。

### 4.2 500 条并发预扫描

在冻结性能负载前 500 条上，对 `budget-200` 执行过一次 `c=1/2/4/8/16/32`、`q=2c` 的探索性
预扫描。结果显示并发 32 的尾延迟明显升高。该阶段仅用于选择资源区间，不作为队列容量消融结论。

## 5. 正式主方法性能对比

### 5.1 配置

| 项目 | 配置 |
| --- | --- |

```bash

```

### 5.2 完整性

- 9 个运行均通过结构完整性验证；
- 每个运行均提交并输出 2000 条记录，结果模型均为 `kg-assist-pro`；
- `full` 和 `budget-200` 均为 2000/2000 成功且无重试；
- `external-schemarag-k10` 每次均为 1998/2000 成功、2 条错误、4 次重试；
- 全部任务级与 RSS 运行级遥测均完整。

SchemaRAG 的错误稳定发生于 `artifact_id=3213` 与 `3214`：模型三次均返回目标 Schema 之外的
字段。这是端到端方法错误，不是 embedding 服务或队列故障，已保留在成功率、重试和尾延迟统计中。

### 5.3 主结果

下表为三次重复均值；吞吐按有效成功记录计算，P95/P99 为各运行分位数的均值。

| 方法 | 成功率 | 平均流水线时间 | 有效吞吐 | 总 Token | P95 延迟 | P99 延迟 | 流水线时间 CV |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `full` | 100.0% | 220.82 s | 9.06 records/s | 1,709,102 | 2437.60 ms | 3601.20 ms | 0.59% |
| `budget-200` | 100.0% | 113.64 s | 17.61 records/s | 1,069,254 | 1160.91 ms | 1307.50 ms | 1.94% |
| `external-schemarag-k10` | 99.9% | 399.68 s | 5.03 records/s | 1,230,411 | 4572.27 ms | 19885.52 ms | 8.26% |

相对 `full`，`budget-200`：

- 流水线时间降低 48.54%；
- 有效吞吐提高 94.38%；
- 总 Token 降低 37.44%。

SchemaRAG 相对 `full` 的总 Token 降低 28.01%，但流水线时间增加 80.99%，有效吞吐降低
44.43%。在线 query embedding 三次平均累计 258.61 s，已纳入端到端流水线时间；Schema 向量
缓存读取或构建时间平均为 8.14 s。

| 方法 | 平均规划时间 | 平均 LLM 时间累计 | 平均 Producer 阻塞 | 平均 RSS 峰值 |
| --- | ---: | ---: | ---: | ---: |
| `full` | 7.81 s | 3504.29 s | 208.70 s | 261.90 MB |

## 6. 端点缩放验证

### 6.1 配置

为控制调用成本，不执行完整三方法四并发矩阵；只比较 `full` 和 `budget-200` 在串行与高并发
边界的表现。SchemaRAG 的在线嵌入、格式错误和尾延迟已由主方法对比覆盖。对应图表
`endpoint_scaling_and_tail_latency` 是一个两面板的端点缩放验证图，不是完整并发扫描：
左面板显示有效吞吐，右面板显示 P99 延迟；现有数据只有 `c=1,q=1` 和 `c=32,q=32`
两个端点。

| 项目 | 配置 |
| --- | --- |
| 负载 | 冻结性能负载前 500 条 |
| 方法 | `full`、`budget-200` |
| 端点 | `c=1, q=1`；`c=32, q=32` |
| 重复 | 每种方法和端点各 2 次 |
| 有效任务与实际调用 | 4000 条，4000 次，无重试 |

首次 `full c=1, q=1` 在此前中止的全矩阵中已完整结束并通过校验，作为第一重复；其余 3500 条
由端点缩放批次补齐。中止的其他全矩阵产物不纳入任何统计。

结果目录：

- `benchmarks/runs/scaling-pro/`：`full c=1, q=1` 第一次重复；
- `benchmarks/runs/endpoint-scaling-pro-low-full/`：`full c=1, q=1` 第二次重复；
- `benchmarks/runs/endpoint-scaling-pro-low-budget/`：`budget-200 c=1, q=1`；
- `benchmarks/runs/endpoint-scaling-pro-high-full/`：`full c=32, q=32`；
- `benchmarks/runs/endpoint-scaling-pro-high-budget/`：`budget-200 c=32, q=32`。

### 6.2 完整性与结果

8 个纳入运行均通过结构完整性验证，每个运行均为 500/500 成功、无错误、无重试，模型均为
`kg-assist-pro`；4000 条任务级遥测与所有运行级 RSS 遥测均完整。

| 方法 | 并发/队列 | 平均流水线时间 | 有效吞吐 | 总 Token | P95 延迟 | P99 延迟 | 流水线时间 CV |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `full` | `c=1, q=1` | 733.49 s | 0.68 records/s | 427,653 | 2086.83 ms | 3034.62 ms | 0.38% |
| `budget-200` | `c=1, q=1` | 463.78 s | 1.15 records/s | 267,358 | 1254.89 ms | 1413.12 ms | 25.32% |
| `full` | `c=32, q=32` | 91.04 s | 5.49 records/s | 427,676 | 7948.04 ms | 12023.53 ms | 0.37% |
| `budget-200` | `c=32, q=32` | 33.89 s | 14.76 records/s | 267,363 | 2654.94 ms | 2822.09 ms | 1.42% |

相对同端点 `full`，`budget-200` 的总 Token 均减少约 37.48%。

| 端点 | 流水线时间变化 | 有效吞吐变化 |
| --- | ---: | ---: |
| `c=1, q=1` | 降低 36.77% | 提高 68.99% |
| `c=32, q=32` | 降低 62.78% | 提高 168.69% |

串行 `budget-200` 两次分别为 346.34 s 与 581.21 s，Token 基本一致但时间 CV 为 25.32%，
说明串行端点会受外部服务延迟波动影响。因此其仅用于验证收益方向，不用于报告精确效应量。

高并发端点的队列平均占用约为 29，接近容量 32。`full` 的 P95/P99 约为 7948/12024 ms，
`budget-200` 为 2655/2822 ms；两种方法 RSS 峰值均约为 262 MB。

由于端点实验同时改变了 Consumer 并发度和队列容量，`c=1,q=1` 到 `c=32,q=32` 的
差异不能拆解为纯并发效应或纯队列容量效应。该实验只支持端点条件下的方向性验证，
不支持队列容量最优值或服务端绝对饱和点结论。

## 8. 离线统计与可复现产物

本节仅读取已通过完整性验证的 `summaries.json`，不发起 LLM 或 embedding 调用。分析脚本为

```bash
.venv/bin/python benchmarks/analyze_performance_results.py
```

生成的论文用数据表位于 `benchmarks/analysis/performance/`：

主实验每组 `n=3`、端点实验每组 `n=2`。脚本对这两种重复次数使用双侧 95% t 区间；因此它是对
重复间服务波动的描述，而不是对模型质量的显著性检验。尤其 `budget-200` 的串行端点波动很大，
其时间相关区间过宽且可跨越物理下界，只保留作方向性验证，不报告为精确效应量。

离线统计复核了主结果：

- 主实验中 `budget-200` 的流水线时间均值为 113.64 s，95% t 区间为 106.94--120.35 s；
  `full` 为 220.82 s，区间为 216.85--224.80 s；
- 两者有效吞吐的均值分别为 17.61 与 9.06 records/s；Token 均值分别为 1,069,254 与
  1,709,102，和第 5 节相对变化结论一致；
- `external-schemarag-k10` 的流水线时间均值为 399.68 s，重复间标准差为 40.42 s，且 P99
  延迟区间很宽，说明其尾部不稳定性不能由均值掩盖；
- 端点统计确认两端 Token 降幅均约为 37.48%，但由于端点同时改变并发与队列容量，不能拆分为
  队列容量的独立效应。

## 9. M1 初始化与 100 条 full 本地规划成本

为补全在线推理之外的部署成本，新增无 LLM 的本地基准脚本
`benchmarks/benchmark_initialization_cost.py`。它将新训练的 100 样本 M1 模型和元数据仅写入
`benchmarks/analysis/initialization/artifacts/`，并显式拒绝向 `models/` 写入；已有
`models/field_selector` 只以只读方式用于加载和规划测量。因此该实验不会污染已用于在线主实验的模型。

执行命令：

```bash
.venv/bin/python benchmarks/benchmark_initialization_cost.py
```

原始结果为 `benchmarks/analysis/initialization/initialization_cost.json`。它不创建 LLM 或 embedding
客户端，测量的边界如下：

- **训练**：训练集的多标签贪心嵌套前缀中取 100 条，seed `42/43/44`；训练 char+word TF-IDF、字段
  Logistic Regression 和长度 Ridge/常数模型，并写入隔离的 `model.joblib`；
- **冷加载**：重复 5 次只读加载线上使用的 `models/field_selector`，另报告隔离 100 样本模型的加载时间；
- **本地 full 规划**：冻结性能负载前 100 条，执行当前 Runner 的 `full` 任务构造路径，包括 M1
  `predict_fields()` 与 Prompt 构造，但不调用 LLM、不入队、不解析响应；
- **在线换算**：仅用第 5、6 节已完成的 `full` 有效吞吐换算 100 条的端到端时间，不把该换算与本地
  规划时间相加。

| 项目 | 配置 | 结果 |
| --- | --- | ---: |
| 100 条 M1 隔离训练 | 3 seeds | 737.13 +/- 43.69 ms，最大 765.86 ms |
| 单个隔离模型文件 | 每个 seed | 3.36 MB |
| 已部署模型冷加载 | `models/field_selector`，5 次 | 178.26 +/- 14.43 ms，P95 197.44 ms，16.22 MB |
| 隔离 100 条模型冷加载 | 每个 seed 各 5 次 | 46.27--47.80 ms 均值，约 3.36 MB |
| 100 条 full 本地规划总计 | 已部署模型 | 366.63 ms |
| 100 条 full 本地规划 | 每条 | 3.09 +/- 0.16 ms，P95 3.25 ms |
| 其中 M1 字段预测 | 每条 | 3.04 +/- 0.16 ms |
| 其中 Prompt 构造 | 每条 | 0.05 +/- 0.02 ms |

在已有在线测量中，100 条 `full` 的端到端时间按有效吞吐换算为：主实验
`c=16, q=16` 约 11.04 s，串行端点 `c=1, q=1` 约 147.26 s。因此本地规划占主实验端到端时间约
3.3%，但该比例随服务端延迟和并发而变；训练和加载是一次性成本，应按部署周期或处理记录数摊销，
不得逐条叠加到在线 Token、延迟或吞吐指标中。

启动成本加入后的性能领先与 break-even 估算见独立记录

## 10. 总结、结论边界与后续工作

已完成的核心证据表明，在 `kg-assist-pro`、冻结负载与单进程异步有界流水线条件下，

本部分的结论限定于当前模型、服务端状态和单进程实现。不能据此宣称：

- 队列容量的最优值或其独立因果效应；
- 服务端的绝对饱和点；
- 故障恢复能力；
- 多进程、多节点或分布式扩展能力。
