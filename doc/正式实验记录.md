# 正式实验记录

## 1. 实验目的

本轮实验检验：在相近的抽取质量下，记录感知的 Adaptive Schema 是否比仅依赖
Prompt 指导模型忽略无信息字段的完整 Schema 方法消耗更少 Token。

本记录只汇总已经完成的正式运行及 Presence 评估结果。它不构成最终的综合抽取
质量结论，因为 LLM Value Score 和 `desc` Embedding Score 尚未完成。

## 2. 固定实验配置

| 项目 | 配置 |
| --- | --- |
| Gold 参考集 | 500 条 `gold_main` 记录 |
| LLM 模型 | `kg-assist` |
| 并发 | `max_concurrency=20` |
| 队列容量 | `queue_size=40` |
| 统一条件 | 相同 raw 输入、模型、temperature、超时、重试及输出解析规则 |
| Gold 性质 | Agent/model-assisted silver reference，不是独立人工 Gold |

比较的方法如下：

| 方法 | 含义 |
| --- | --- |
| `full` | 完整 18 字段 Schema，基础 Prompt |
| `prompt-null` | 完整 Schema，要求无可靠信息时输出 `null` |
| `prompt-omit` | 完整 Schema，允许省略无可靠信息字段 |
| `fixed-5` | 固定输入 5 个字段 |
| `fixed-10` | 固定输入 10 个字段 |
| `budget-200` | 预测字段成本约束为 200 的 Adaptive Schema |
| `budget-400` | 预测字段成本约束为 400 的 Adaptive Schema |
| `lambda-0.003` | 无硬预算、以效用减预测成本选择字段的 Adaptive Schema |

## 3. 样本与运行状态

正式任务计划覆盖 500 条记录和 8 种方法，共 4000 个任务。

- `fixed-10`、`budget-200`、`budget-400`、`lambda-0.003`：各 500 条成功。
- `full`、`prompt-null`、`prompt-omit`：各 499 条成功。
- `fixed-5`：主运行 499 条成功；恢复运行中 `artifact_id=6703` 成功。
- `artifact_id=6703` 的 `full`、`prompt-null`、`prompt-omit` 在五次重试后仍出现
  JSON 解析失败。因此，八种方法的主配对分析统一限定为 499 条共同成功记录，
  不将该记录混入主比较。

`prompt-omit` 在第二轮正式结果中没有 Schema 外字段，但存在部分字段省略及少量
无依据占位字符串风险；后续 Value Judge 需将其作为错误或无依据输出诊断，不能将
其直接视为 `null`。

## 5. 当前可报告结果

在当前 Gold 的 Presence 维度上，`budget-200` 相较两种 Prompt-only 基线均更节省
Token：

- 比 `prompt-null` 少 309.26 平均总 Token，减少 37.10%。
- 比 `prompt-omit` 少 341.73 平均总 Token，减少 39.46%。
- `budget-200` 的 Presence Micro-F1 为 0.7126，高于 `prompt-null` 的 0.4966 和
  `prompt-omit` 的 0.5824。

因此，当前结果支持以下受限结论：在这 499 条共同成功记录及 Presence 评估维度上，
`budget-200` 的 Adaptive Schema 相较 Prompt-only 基线具有更低的实际 Token 消耗，
且字段存在性 F1 更高。

不能据此宣称最终抽取质量全面更高，或宣称对所有 Schema 预算均成立。特别是
`budget-400` 的 Presence 结果低于预期，需要在后续评分和诊断中单独分析。

## 6. 尚未完成的正式评分

冻结的综合质量定义为：

```text
Quality = 0.5 x Presence-F1
        + 0.3 x LLM-Value-Score
        + 0.2 x Desc-Embedding-Score
```

当前仅完成第一项及旧的辅助 `exact_value_recall`。后续仍需：

1. 对非 `desc` 字段实施 LLM Value Judge，并保存字段级评分、理由、模型版本和 Prompt
   hash。
2. 对 `desc` 实施固定 embedding 模型的余弦相似度评分。
3. 计算三部分 Quality，并对同一 `artifact_id` 做质量-Token 配对比较。
4. 配置实际输入、输出单价，或基于已记录 Token 离线换算货币成本。

## 8. 结果使用边界

- Gold 由强模型和 Agent 辅助生成，存在共享模型偏差，论文中应表述为
  model-assisted reference 或 silver reference。
- 当前费用字段为 0，仅可直接比较 Token；`C_actual` 的 Token 记录包含重试，货币费用
  需在设置价格后另行换算。
- 本轮固定并发为提升运行速度的运行配置，不可将墙钟吞吐差异作为 Schema 方法本身的
  优势。
- 主结论必须以 499 条共同成功样本为单位；500 条全量统计只可作为运行完整性或辅助
  诊断使用。

## 9. Prompt 消融：移除重点字段说明

### 9.1 动机与实现

第二轮正式实验中的基础 Prompt、`prompt-null` 和 `prompt-omit` 都包含“重点字段说明”段落，
并要求模型对这些字段优先查找、归纳或合理补全。为区分 Schema 长度效应和该段指令效应，
新增了不包含重点字段说明的三套模板：

- `1_no_focus.prompt`：完整 Schema，字段无可靠依据时输出 `null`。
- `1_no_focus_null.prompt`：完整 Schema，明确先判断源数据依据，再输出 `null`。
- `1_no_focus_omit.prompt`：完整 Schema，无可靠依据时省略字段。

新版模板只允许依据 raw 中明确出现或可直接归纳的信息，不允许使用外部知识或领域常识补全。
旧模板和 v2 结果未修改。v3 通过新的 Prompt hash 及 `experiment_id=gold-main-v3-no-focus`
与历史结果隔离；runner 的 `focus_schema` 元数据在新版模板中为空。

### 9.2 单条与 10 条冒烟结果

使用 `.venv/bin/python`、与正式实验相同的模型和默认 temperature，结果写入 `/tmp` 临时文件，
未写入 v2 正式结果。单条测试中 3 个方法均成功，未发生重试；10 条测试共 30 个任务均成功，
未发生 JSON 解析或字段结构错误。

| 方法 | 成功数 | 全空数 | 全空率 | 平均非空字段数 | 平均 Input Token | 平均 Output Token |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `full`（无重点字段） | 10 | 8 | 80% | 3.60 | 561.50 | 113.90 |
| `prompt-null`（无重点字段） | 10 | 8 | 80% | 2.90 | 562.50 | 112.70 |
| `prompt-omit`（无重点字段） | 10 | 0 | 0% | 17.10 | 580.50 | 158.30 |

该冒烟结果只用于诊断，不作为正式质量比较。它显示：删除重点字段说明后，`full` 和
`prompt-null` 的全空行为仍然存在；`prompt-omit` 虽然避免了全空，但仍有明显过度填充，
包括将字段描述文本直接作为输出值，以及输出 raw 未明确支持的“传世”“中原文化”等值。
因此，后续正式重跑前仍需先决定是否进一步调整 Schema 描述、输出约束或解码参数，不能把
本次 Prompt 消融直接解释为质量改善。

### 9.3 `kg-assist-pro` 冒烟测试状态

随后使用相同的 10 条样本、无重点字段 Prompt 和其他实验参数，仅将模型临时覆盖为
`.env` 中的 `LLM_MODEL_pro=kg-assist-pro`，运行 3 种方法共 30 个任务。该轮没有形成可用的
模型结果：30 个任务均在重试后失败，服务端返回 HTTP 400，错误为：

```text
could not auto resolve a provider for the request, please specify a provider explicitly
```

这表明当前网关无法自动解析 `kg-assist-pro` 对应的 provider，属于部署或路由配置问题，
不是 Prompt、上下文窗口或 JSON 解析问题。因此本轮不能据此评价 `kg-assist-pro` 的抽取能力，
也未将失败记录混入任何质量统计。后续需要从服务端确认该模型的准确模型名及 provider 配置后，
再进行同条件冒烟测试。

随后再次重试 `kg-assist-pro`：网关已不再返回 provider 路由错误，但 10 条样本、3 种方法共
30 个任务仍全部失败，错误为 `JSONDecodeError: Expecting value: line 1 column 1`，说明响应为空
或不是可解析的 JSON。进一步将 `LLM_TEMPERATURE` 临时设置为 `0`，对 1 条样本运行 3 个任务，
结果仍全部在 1 次重试后以相同的 `JSONDecodeError` 失败。以上结果仍不能用于评价模型抽取能力，
需要先确认该模型服务是否支持当前 Chat Completions 请求及 JSON 输出协议。

### 9.4 关闭 Qwen3 思考后的验证

确认 `kg-assist-pro` 实际为 Qwen3-8B 后，在 `llm_runner.py` 的 Chat Completions 请求中加入：

```python
extra_body={
    "chat_template_kwargs": {
        "enable_thinking": False,
    }
}
```

同时在解析器中兼容 `<think>...</think>` 包裹的响应，以防服务端忽略关闭思考参数。使用
`LLM_MODEL=kg-assist-pro`、`LLM_TEMPERATURE=0` 和 1 条样本进行 3 个方法的验证，结果全部
成功且无重试、无 JSON 解析错误：

- `full`：Input 566、Output 119，结果全为 `null`。
- `prompt-null`：Input 567、Output 119，结果全为 `null`。
- `prompt-omit`：Input 585、Output 70，抽取出 5 个非空字段。

相比之前包含约 599 个思考 Output Token 的原始响应，关闭思考后响应已可直接解析，说明该
参数已生效。它解决的是思考文本导致的 JSON 协议失败和额外 Token 消耗，不代表已经解决
`full` 方法的全空输出问题；后续仍需通过 10 条冒烟和正式评分判断模型能力。

进一步使用相同配置运行 10 条样本、3 种方法共 30 个任务，结果如下：

| 方法 | 成功数 | 错误数 | 全空数 | 全空率 | 平均非空字段数 | 平均 Input Token | 平均 Output Token |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `full`（无重点字段） | 10 | 0 | 3 | 30% | 9.10 | 565.50 | 158.60 |
| `prompt-null`（无重点字段） | 10 | 0 | 7 | 70% | 4.20 | 566.50 | 137.80 |
| `prompt-omit`（无重点字段） | 4 | 6 | 0 | 0% | 10.25 | 583.50 | 112.75 |

6 个失败任务均因返回了 Schema 外中文键 `文物名称` 而被 runner 拒绝。关闭思考后，`full`
全空率从此前 10 条测试的 80% 降至 30%，说明 Qwen3-8B 的思考过程确实会影响有效抽取表现；
但 `prompt-null` 仍有 70% 全空，`prompt-omit` 的结构遵循仍不稳定。因此该轮仍只作为模型与
请求配置诊断，不能直接并入正式质量统计。

### 9.5 稳定版 Prompt 与当前连接阻断

为得到可稳定运行的单一实验版本，新增稳定版模板：`1_stable.prompt`、
`1_stable_null.prompt` 和 `1_stable_omit.prompt`。普通字段只向模型提供英文键名；
`dynasty`、`category`、`material`、`form_type`、`usage` 与 `craft_school` 仅提供简短中文说明。
这样避免将完整 Schema 的长字段描述作为模型可复制的候选值，同时保留重点字段的最小语义提示。

本地结构验证已通过：三套模板最终 Prompt 均不包含内部标记或普通字段的长描述，重点字段说明
仅包含预定义短语，且 `focus_schema` 元数据与实际输入一致。语法检查
`python3 -m py_compile llm_prompt.py llm_runner.py` 和 `git diff --check` 也通过。

随后使用 `LLM_MODEL=kg-assist-pro`、`LLM_TEMPERATURE=0`、关闭思考、单条样本、
`max_concurrency=1` 与 `max_retries=0` 重试 `full`、`prompt-null`、`prompt-omit`。三个任务均以
`APIConnectionError: Connection error.` 失败，且没有返回 Token 或模型内容。此前的 10 条稳定版
测试也全部遇到同一连接错误。因此该稳定模板尚未取得可评价的模型输出，当前阻断为网关或模型服务
连通性，而不是 Prompt 结构、输出解析或并发配置问题；失败结果未混入任何质量统计。

### 9.7 有限重试与效率口径

从 v3 稳定版起，每个任务采用“首次请求加最多 2 次重试”的固定策略，即最多 3 次尝试。
单次 JSON 解析或 Schema 校验失败不立即计为最终失败；只要后续尝试成功，任务即为最终成功。
每次尝试的 Token、延迟、错误与状态写入 `attempts`，任务顶层 Token 与延迟为全部尝试的累计值。

效率报告同时记录最终成功率、最终失败率、重试任务数、总重试次数、总尝试次数、每个提交任务的
平均累计 Token，以及每个最终成功结果的累计 Token。达到重试上限仍失败的任务计入最终失败率，
其已经消耗的成本仍计入总成本。

在 10 条稳定版复验中，`full` 和 `prompt-null` 均为 10/10 最终成功且无需重试；
`prompt-omit` 为 8/10 最终成功，2 个任务在 3 次尝试后仍为 `JSONDecodeError`，共发生 4 次重试。
其每条提交任务的平均累计 Token 为 676.00，不能仅以成功样本的 93.75 Output Token 评价效率。

## 10. v3 稳定版正式实验

### 10.1 固定配置与产物

正式运行使用 500 条 `gold_main` 记录、`LLM_MODEL=kg-assist-pro`、`LLM_TEMPERATURE=0`、
关闭 Qwen3 思考、`max_concurrency=20`、`queue_size=40`，并使用稳定版 Prompt 和有限重试策略。
方法为 `full`、`prompt-null`、`prompt-omit`，共提交 1500 个任务。实验标识为
`gold-main-v3-stable-pro`，结果文件为 `experiments/gold_main_v3_stable_pro_results.jsonl`；
评估报告为 `reports/gold_main_v3_stable_pro_paired_metrics.json`。本轮不覆盖 v2 结果。

### 10.3 476 条共同成功样本的 Presence 诊断

三种方法共同成功的记录为 476 条。下表仅评估字段存在性，不评价具体字段值正确性；
`Presence Macro-F1` 是记录级 F1 的均值，名称沿用历史报告。

| 方法 | Presence Macro-F1 | Presence Micro-F1 | Presence Precision | Presence Recall | 平均总 Token |
| --- | ---: | ---: | ---: | ---: | ---: |
| `full` | 0.7623 | 0.7410 | 0.6086 | 0.9469 | 539.83 |

M1 将 Micro-F1 提高 0.0217，长度 MAE 降低 0.0431，Budget-200 覆盖仅提高 0.0017；但

因此 M1 不替代原始模型，当前结论是“小样本性能提升需要针对长尾字段的模型策略”。

### 19.4 结论与解释边界

在当前统一的 stable Prompt 和 `kg-assist-pro` 配置下，M1 + budget-200 取得最好的整体
质量-Token 平衡：相对于 M1 + lambda=-0.003，总 Token 减少约 16.6%，Micro-F1 提高约
0.0129；相对于 M1 + budget-400，总 Token 减少约 21.8%，Micro-F1 提高约 0.0344。

lambda=-0.003 和 budget-400 均保持约 0.99 的 Gold 字段覆盖率，但未带来更高的最终抽取
质量。budget-400 反而出现较低的 Presence 和 Exact Value Recall，说明候选字段覆盖率不等于
最终抽取质量，增加字段还可能引入无效字段和模型干扰。

因此当前 M1 策略定位为：`budget-200` 作为主方案，lambda 作为高覆盖率、较高 Token 的保守
对照，budget-400 作为高覆盖率但质量和稳定性较差的反例。这里的“质量”仅指 Presence 和
Exact Value Recall；Value Judge、描述 embedding、综合 Quality 和真实货币成本尚未纳入。
历史 FullSchema 指标来自相同 476 个 `artifact_id`，但调用批次不同，因此本节结果作描述性
配对比较，不作严格统计显著性结论。FullSchema 训练标签仍属于 silver/model-assisted reference，
`estimated_field_cost` 也只是离线字段成本估计，不是实际 API 成本。
